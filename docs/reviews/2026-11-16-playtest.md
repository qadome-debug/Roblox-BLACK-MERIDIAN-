# Play-test review — 2026-11-16

Build: `main` after BM-069, plus the fixes in this change. Tested in Roblox
Studio 0.747 (play mode: one server, one client) and with the headless
suite (`check-all`).

A passing technical test proves the wiring works. It does not prove a
gameplay feature is finished. Nearness, Verses, Dissonance and Burdens still
run on placeholders or have no canonical content; see "Not accepted" below.

## How it was run

The default build cannot exercise gameplay in Studio: an unpublished place
has no DataStores, so profiles fail to load and every gameplay request is
`NOT_READY` (by design). The play-test therefore uses a separate build:

- `playtest.project.json` adds a baseplate, a spawn, the test tree, a
  client driver and a control RemoteFunction. None of this is in
  `default.project.json`.
- `src/tests/Playtest/Server.luau` gives Bootstrap in-memory DataStores
  (Studio only) and answers privileged setup and state-read commands.
- `src/tests/Playtest/Client.luau` runs a scripted scenario through the
  real client `Net` controller, so every request crosses the real remotes,
  dispatcher, rate limiter, validators and adapters.
- `src/tests/Playtest/RunnerPlugin.luau` (optional) starts play mode by
  itself through `StudioTestService`. It was copied into the local plugins
  folder for the run and removed afterwards.

The PC screen was locked during the run, so results were read from the
Studio log, not watched. Nothing visual (camera, avatar appearance, UI) was
inspected.

Harness shortcuts, because the real flows do not exist yet:

- "grantNearness" unlocks Nearness on the profile. The starter Cant
  selection flow (BM-106) is not built, so no player can own a Cant in
  normal play.
- "activateCant" calls the server activation directly. No client request
  for activating a Cant has been specified.

## Bug found and fixed

**Saved Cant was not restored after a rejoin.** `CantEquip` wrote the
profile and the combat layer, but nothing copied the saved value back into
combat when a player joined again. After a rejoin the profile said
"equipped", combat said "nothing equipped", activation failed and a new
equip was refused as a duplicate. Fixed with `Services/Loadout.restore`,
called when the profile becomes ready and when the combatant is added.
Covered by `Integration/Reconnect.test.luau` and by the Studio reload
checks.

## Not tested in Studio

- A real reconnect (leave the server and join again). Play mode cannot
  rejoin; the profile half was simulated on one server, and the session
  half (new epoch, stale epoch refused) is covered headless.
- Real DataStores. That needs a published place with Studio API access.
- A successful Verse cast, cast interruption, and Dissonance raised by a
  Verse. No canonical Verse exists, and test Verses cannot pass the real
  validators. These paths are covered headless with fixture catalogs only.
- Anything visual, and more than one client.

## Known gaps that are later tasks, not bugs

- Combat death and the Roblox character are not linked, and there is no
  respawn request yet.
- The client has no input bindings or UI; it only receives state.
- `CombatInput` does not check an equipped weapon (inventory is BM-080).
- The own combat view does not carry Cant cooldowns or the Dissonance
  meter.

## Design specifications needed

The repository holds one design source, `docs/technical-plan-2.0.md`. It
states that the canonical content inventory is not included, and it names
no mechanic for Nearness, any Verse, Dissonance or any Burden. The exact
list is in `docs/task-log.md` under "Design specifications needed".

## Second pass, same day: on-screen run and follow-up review

The screen was unlocked for this pass, so the play-test was watched in
Studio instead of read from the log.

- The avatar spawns on the baseplate, the default camera follows it, and
  the character walks and jumps. The character position was read before
  and after moving and had changed.
- The scripted run passed 52 of 52 with the code changed in this pass.
- Nothing of the game is visible yet. There is no HUD, no health or
  stamina display, and no animation or effect for combat, Cants or
  Dissonance. Enemies exist only in the simulation and have no body in the
  world. The only on-screen element is the result overlay of the test
  driver, which covers the left half of the view and is test scaffolding.
- A `PlaytestStayOpen` Workspace attribute was added to the harness so a
  session can stay open after the scripted run for looking around by hand.

Follow-up work from this pass is recorded in `docs/task-log.md` under
"Review 2026-11-16 (second pass)": the BM-047 receipt archive audit (five
defects fixed), the production isolation check for the play-test tools,
and the acceptance review that separates "built" from "accepted".

Still not tested, and not possible in an unpublished place: real
DataStores, a real leave-and-rejoin, more than one client. These wait for
a staging place and the owner's approval.
